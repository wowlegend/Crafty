# Crafty — One Material Grammar (Phase 2, roadmap 9) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every block surface speaks one bold-flat pixel-art language: textures are a few solid, clustered tones
instead of per-texel static; a grass or snow hillside shows a dirt (or stone) wall under a turf (or snow) lip;
tree trunks show bark on their sides and rings on top; and meadow tufts are spread evenly across every chunk with no
bald strip and no visible 2 m grid.

**Architecture:** Three independent seams, each pure and node-testable where the shader cannot be: (1) the texture
generator paints each layer from a declared tone table, holding each layer's average colour so the palette stays the
light-and-colour lane's; (2) the terrain VERTEX stage derives each face's role (top, side, bottom) from its axis
normal and reads the face's TEXTURE LAYER from a const table generated by the pure `materialGrammar.js` (the JS mirror
the node gates read), while the greedy mesher only maps `v` to world-up on every side face, so the fragment stage only
swaps which layer it samples; `colors.b` is NOT used here, because the lantern lane (Phase 3, roadmap 12) owns it for
the face light level (review amendment 1); (3) the grass sampler becomes a stratified, world-keyed, density-preserving
reservoir with tufts centred on their own column.

**Tech Stack:** three r172 `DataArrayTexture` + `MeshStandardMaterial.onBeforeCompile` (GLSL ES 3.0), the greedy
mesher in the terrain worker, vitest (node), Playwright (e2e + the lookbook probe), puppeteer probes.

**Spec:** umbrella `docs/superpowers/plans/2026-10-27-crafty-masterpiece.md` (Phase 2, "One material grammar");
design inputs `docs/superpowers/masterpiece-2026-10/roadmap-2026-10-27.json` (move rank 9: `what`, `lived_proof`,
`heat_budget`, `threat`, `door`), `refute-2026-10-27.md:100` (verdict KEEP: the bald strip confirmed by arithmetic;
no mipmap entry in DECISIONS.md), `upside-2026-10-27.md:88,95` (L3, L10). Where they differ, the umbrella wins.

seeded from the colours the generator already declares, plus one new tone where named:

|---|---|---|
| grass | base `86,124,53`, shade `65,105,40` (`:64-66`), light `104,146,62` (new) | blade clumps: 3-6 px lighter tufts over base, shade gaps |
| dirt | base `151,109,77`, shade `115,88,66` (`:75-77`), light `170,126,90` (new) | clods (3-5 px shade blobs) and sparse 2x2 light pebbles |
| stone | base `104,104,107`, light `132,132,135` (`:87-90`), crack `78,78,82` (new) | chunky facets (light/base) cut by 1 px cracks |
| sand | base `200,180,128`, light `216,196,140`, shade `184,164,116` (range `:99-101`) | quantised ripples, period dividing 32 |
| snow | base `236,238,250`, drift `214,224,244`, glint `248,250,255` (`:110-113`) | soft cool drifts, rare 1 px glints |

The table is a starting point the implementer tunes in the lookbook; the gates hold the rules, not the values:
2-4 tones per material; composite layers (ores, face variants) use only their parents' tones; a same-tone neighbour
ratio of at least 0.55 (today 0.012-0.110); continuous tiles wrap seamlessly, framed tiles (glass, wood top) have a
one-tone border; no texel darker than 0.35x its layer's mean luminance unless it is an `ORE_TILES` ore colour or its shade;
**each layer's linear luminance within ±15% and chromaticity within ±0.03 of today's** (a frozen fixture). The mean
pin is the decision that keeps this move out of the light-and-colour lane's way: the far field (`farField.js:85-106`),
the biome-tint balance, the grass blade's measured match to its turf, and the light rig all keep their inputs; only
the structure changes. Stone and the ore matrix stay grey below the ore glow's 0.08 chroma edge; nugget tones stay
above 0.18. Water (9) and air (0) are left untouched and declared so.

**M2 — Face grammar, derived in the vertex stage from a generated table.** (Amended 2026-10-27, review amendment 1.)
The first draft baked the layer into `color.b` in the mesher; the lantern plan already claims that channel for the face
light level, so the two would overwrite each other (lit faces would sample arbitrary layers, unlit sides layer 0 =
air, black). The layer is now derived where the roadmap's `what` put it, "from the normal" in the terrain shader:
the vertex stage reads `color.r` (block type) and the `normal` attribute, computes the role (`normal.y > 0.5` top,
`< -0.5` bottom, else side), and reads `FACE_LAYER[block * 3 + role]` from a GLSL `const float` array that
`materialGrammar.js` GENERATES from the same `Uint8Array` table the node gates read. The table, its literal mapping and
the generated array are node-testable; only the six-line role expression is GPU-only, and the probe page (Unit 2
Step 7) renders it on Chromium and WebKit. Object-space normals are unaffected by the chunk group's transform, so a
rotated chunk would still work. No merge-key change and no mesher write: a merged quad never mixes roles (different
axes are different sweeps, `dirFlag` is in the key) or block types, so the per-vertex lookup is constant per quad.
`colors.b` stays free for the lantern.
- `src/world/materialGrammar.js` (new, pure) declares the roles (top 0, side 1, bottom 2), the variants
  `grass_side` (grass sides), `snow_side` (snow sides), `wood_side` (wood sides), the remaps grass bottom -> dirt,
  snow bottom -> stone, and derives `BLOCK_LAYER_COUNT = max(BLOCK_ID) + 1` and
  `TEXTURE_LAYER_COUNT = BLOCK_LAYER_COUNT + variants` through a factory `buildGrammar(blockIds)` whose default export
  is `buildGrammar(BLOCK_ID)`, so a test drives the derivation with an extra id directly (`BLOCK_ID` is frozen,
  `blockIds.js:27`). Variant layers sit AFTER the block-id space, so the lantern (roadmap 12, id 16) shifts them by one
  with no edit here.
- Snow sides use stone because snow columns are stone underneath (`src/world/biomeTable.js:38`, secondary 3;
  `terrain.worker.js:420-426`); grass sides use dirt (`biomeTable.js:39-47`, secondary 2).
- The base layer stays the block's top: the far field averages it (`farField.js:106`), and wood's base layer becomes
  the ring top while `wood_side` is bark.
- The turf/snow lip is AUTHORED in the variant layer (rows 28-31 always turf, drips into rows 26-27 in about a third
  of columns), not composited in GLSL: one fetch, no branch, hand-shaped. `LIP_TEXELS = 4`.
- The X-face UV push becomes `(0,0, 0,w, h,w, h,0)` so `v` rises with world Y on all four side directions and row 0
  is each block's bottom. Lengths are unchanged, so the 1:1 gate stays green; a new orientation gate pins direction.
- The shader keeps `layerIndex` (block type) for the tint, the ore glow and the leaf feel, and samples a new
  `texLayer = floor(vTexLayer + 0.5)` from a flat varying fed by the vertex-stage table lookup (block index clamped to
  `BLOCK_LAYER_COUNT - 1`, so an out-of-range id never indexes past the array). The tint stays keyed by block type: a
  grass side's dirt body takes the grass biome hue exactly as dirt blocks already do (dirt is tinted,
  `terrainTint.js:23`); a snow side's stone body takes the snow biome's near-white tint (strength 0.35,
  luminance-normalised) — accepted, stated in Risks.

**M3 — Grass spread.** `grassTops` scans every column (stride gone). Each grass column gets a key
`hash01(worldX, worldZ, GRASS_SELECT_SALT)` (the existing integer hash, `grassVariation.js:70`, a new salt 6) and a
stratum `floor(x/4) + ceil(size/4)*floor(z/4)`. Candidates are ranked by key inside their stratum; all candidates are
ordered by `(rank, key)` and the first `keep = min(cap, floor(n / density))` are kept, where `n` is the chunk's grass
column count and `density = GRASS_DENSITY_DIVISOR = 4`. **The divisor is what holds the GPU cost** (amended, review
amendment 2): today's stride-2 lattice samples one column in four, so a partly-grassed chunk (forest floor, biome
edge, beach fringe) gets about `n/4` tufts; dropping the stride while keeping `min(cap, n)` would give it up to 4x that.
Measured 2026-10-27 (`<session scratchpad, not kept>/grass-density.mjs`,
160 chunks): today 5,176 tufts; `floor(n/4)` 5,172; `ceil(n/4)` 5,240; `min(50, n)` 6,896. On an all-grass chunk
`floor(256/4) = 64`, so `keep = 50` exactly as today, and the strata deal 3 tufts to every 4x4 stratum before any gets
a 4th, so no aligned 4x4 cell is ever bald. Keys come from the world position, so the result does not depend on scan
order. One block edit changes at most 3 tufts: at most 2 with `keep` fixed (derivation in Unit 3), plus one when `n`
crosses a multiple of 4 and `keep` steps by one (asserted over 500 edits). Cap stays 50, one constant
`GRASS_TUFTS_PER_CHUNK` read by both worker sites (which pass `{}`) and the consumer. Blades centre on
`x + 0.5, z + 0.5` with `JITTER_MAX = 0.5 - (BLADE_WIDTH / 2) * SCALE_MAX` (= 0.244), so a whole blade base stays on
its own column at any yaw and scale. On all-grass chunks the total is unchanged and density per column falls about 19%
where rows 0-12 were filled (50 over 256 columns instead of over about 208); on partly-grassed chunks the expected
count is today's.

**Interfaces:**
- Consumes: `hash01(x, z, salt)` (`grassVariation.js:70`).
- Produces: `grassTops(topCodes, topYs, size, originX, originZ, { cap = GRASS_TUFTS_PER_CHUNK, stratum = GRASS_STRATUM,
  density = GRASS_DENSITY_DIVISOR } = {}, biomeIds = null) -> Array<[x, y, z, biomeId]>` in `(rank, key)` order;
  `BLADE_WIDTH`, `JITTER_MAX`, `GRASS_TUFTS_PER_CHUNK`, `GRASS_DENSITY_DIVISOR` exported. A caller that passes
  `stride` gets nothing from it (there is no such option); that is why E3 below mutates the sampler, not a call site.

The selection (the only algorithm the tests do not determine): candidates = columns with
`topCodes[i] === GRASS_CODE`, `n` of them; `key = hash01(originX + x, originZ + z, GRASS_SELECT_SALT)`;
`stratum = floor(x / s) + floor(z / s) * ceil(size / s)`; `rank` = position by ascending key inside the stratum (ties
by `i`); order all by `(rank, key)`; keep the first `keep = min(cap, floor(n / density))`. Stability with `keep` fixed:
removing column c from stratum S lowers the rank of S's later items by one; if c was kept, exactly one item (S's next,
or the next in the global order) takes its place; if it was not kept, nothing kept moves (keys ascend with rank inside
a stratum, so S's next item cannot jump a level-L prefix its predecessor missed). So a fixed `keep` changes at most 2
tuples; `keep` itself moves by at most 1 per edit (when `n` crosses a multiple of `density`), adding or dropping one
more at the boundary. One edit changes at most 3 tuples.
